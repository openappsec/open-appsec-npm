## Outcomes summary

- Phases 1–6 ported the open-appsec integration onto the v2.14 base (backend
  ESM modules, schemas, migrations, frontend chrome, settings page, proxy-host
  modal config tab, location overrides, log section).
- Phase 7 (this phase) bumped versions, audited static surfaces, and produced
  the audit doc. Runtime validation is deferred.

## Phase 7 — Deferred to runtime validation

The following items could not be exercised on the current Windows shell because
no reachable Docker daemon is available. They are the **first** validations the
user should run in a Docker-capable environment:

- [ ] `docker build` of `docker/Dockerfile` (main NPM image) succeeds and
      produces a runnable image.
- [ ] `docker build` of `docker/Dockerfile.central-mgmt` succeeds and produces a
      runnable image.
- [ ] `cd deployment && docker compose up -d` brings the stack online with
      `npm-attachment` + `appsec-agent` healthy.
- [ ] Backend migrations run cleanly against a fresh SQLite DB
      (`backend/migrations/20260513120000_open_appsec.js` applies without
      error).
- [ ] Cypress e2e suite (`./scripts/ci/fulltest-cypress`) passes against the
      built image.
- [ ] WAF activation curl test (per plan Phase 7.4): enable open-appsec on a
      proxy host, send a request matching a known attack pattern, verify the
      agent blocks it.
- [ ] Open-appsec log streaming: confirm entries appear in the four log tabs
      (All / Important / Detailed / Notifications) after a blocked request.

Until those boxes are checked, the build is considered code-complete but not
runtime-validated. The audit document records the same list under "Runtime
smoke checklist for the user".
